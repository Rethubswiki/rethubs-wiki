# Resource Entry Template

Use this template for a record that has enough source material to be reviewed. A directory, store or community list may appear as **discovery source**, but it cannot replace the canonical project link for a factual field.

```markdown
# Resource name

> One narrow sentence describing the role; never a broad recommendation.

**Tags:** [app](Tags-and-Discovery#resource-type) · [audio](Tags-and-Discovery#medium) · [android](Tags-and-Discovery#platform)

| Field | Recorded value |
|---|---|
| Role | App, extension, source, directory, server, integration, store, guide or index |
| Canonical origin | URL and project owner |
| License | Declared license, or **unconfirmed** |
| Platforms | Declared or observed platforms, with the evidence scope stated |
| Relationship | Host-app, server or local-library boundary, if applicable |
| Languages | Only verified declared languages |
| Discovery source | Credited community index or store, if one led to the candidate |
| Last review | YYYY-MM-DD |
| Evidence label | Declared, observed, inferred or unconfirmed |

## What the source supports

State the verified function in narrow terms. Link the canonical material in References.

## Compatibility and limits

Record dependencies, archival status, installation limits, duplication risk or unanswered questions. Do not turn an observed relationship into a universal compatibility claim.

## References

1. [Canonical project](https://example.org)
```

Do not include private data, credentials, local browser state, unsupported claims, ratings, inferred security assessments or invented user feedback.
